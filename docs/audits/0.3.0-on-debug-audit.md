# Internal audit: section instructions, debug trace and interpolation (0.3.0)

Scope: what came with phase 0, the `on*` instructions, the debug trace and
interpolation (names with `_`, expressions in numeric parameters), plus the older
code paths this code started to exercise. Every finding was reproduced before any
fix. Performance numbers: release build, 2 vCPU Xeon 2.1 GHz; they compare before
and after on that machine and are not absolute values.

Summary:

| # | Kind | Finding | Severity |
| --- | --- | --- | --- |
| 1 | Bug | `end` inside `cblk` or `iter` does not stop the following instructions of the block or loop | High |
| 2 | Bug | The bytecode reader applies different nesting limits from the text parser | High |
| 3 | Performance | `[[ ]]` copies every variable of the context on each evaluation | High |
| 4 | Performance | Nested instructions are bound again on every run (a regex recompiled per iteration) | Medium |
| 5 | Performance | The line scanner decodes UTF-8 character by character | Medium (not changed: no proven gain) |
| 6 | Performance/memory | The debug trace has no limit of steps per container | Medium |
| 7 | Observation | Line and character errors copy the whole document into the message | Fixed later in 0.3.0 |

---

## 1. `end` inside blocks and iterations

**Cause.** `run_tokens` (phase 0) became the stopping rule of the root: after
`end`, no following instruction runs. But `cblk` and `iter` have their own loops
(`for token in tokens` in `cblk/mod.rs`, `for i in 0..times` in `Iter::run`) that
did not check `context.is_halted`. `end` marked the context and the inner loop
went on.

**Reproduction.**

```text
blk b assoc ate x;
blk b assoc end;
blk b assoc ate y;
cblk b;
ate z;
```

Input `""` → output `"xy"`. By the semantics of `end` (stop the pipeline) the
expected result is `"x"`: `ate z` (root) does not run, but `ate y` (same block,
after `end`) did. With `blk b assoc iter 3 times end;` + `blk b assoc ate y;`, the
output was `"y"`: the remaining iterations and the next instruction of the block
ran.

**Implications.** The same `end` had a different effect depending on the level it
appears at, and the pipeline kept changing the text after "ending". With `ppjn`
(phase 5, `end` local to the joined pipeline) the difference would become even
more confusing. It contradicted the documented contract of `run_tokens`.

**Fix.** `cblk` runs its body with `run_tokens`; `Iter::run` stops before the next
iteration when the context is halted. Tests reproduce both cases. Behavior change,
recorded in the changelog.

## 2. Different nesting depth between text and bytecode

**Cause.** The text parser starts the root at depth 0, and the parameter of a
`blk` enters *assoc payload* mode (limit 3). The bytecode reader
(`decode_param_record_to_valtype` in `src/bytecode/reader.rs`) decoded the
instruction parameter of each root instruction with
`TextForgeParamTypes::from_bytecode`, which starts at depth 0 **in normal mode**,
without knowing whether the parent is a `blk`. As a result the direct child was
counted one level above its real depth, and the payload of `blk` used limit 1
instead of 3.

**Reproduction.**

| Pipeline | Text | Bytecode (before) |
| --- | --- | --- |
| `iter 2 times onln 1 apply tbs;` | rejected (depth 2 > 1) | **accepted** |
| `blk b assoc iter 2 times onln 1 apply tbs;` | accepted (3 ≤ 3) | **rejected**: `Nested token depth exceeded` |

The second case already existed on `main` (`blk b assoc iter 2 times ifdc x do ate y;`).

**Implications.** A valid pipeline saved as `.textforgebc` did not load (including
the documented pattern `blk … iter … onln '[[__COUNTER__ + 1]]' …`), and a
bytecode file could contain a structure the parser and the builder refuse.

**Fix.** The reader decodes the instruction parameter of the root at depth 1, in
*assoc payload* mode when the instruction's signature is a block's: exactly the
rules of the text parser. Round-trip tests for both cases.

## 3. `[[ ]]` copies every variable on each evaluation

**Cause.** `expr()` (`src/utils/expr.rs`) called `build_eval_context` with every
variable of the context and cloned each text value into a new `HashMapContext`,
for each `[[ ]]` resolved. The cost was proportional to the size of **all**
variables, not of those the expression uses.

**Reproduction.** `iter 2000 times ate '[[__COUNTER__ % 10]]';`: 3.7 ms per run.
With a 1 MB variable declared first (`val big = …`) and not used in the
expression: 89 ms (24×).

**Implications.** Expressions in numeric parameters (newly added) are used
precisely in loops (`onln '[[__COUNTER__ + 1]]'`): the cost of each iteration grew
with everything the pipeline keeps in variables.

**Fix.** Compile the expression (`evalexpr::build_operator_tree`), list the
variables it reads (`iter_read_variable_identifiers`, an API confirmed in the
evalexpr 13 documentation) and build the context with those only. Error messages
are unchanged: `eval_with_context` performs the same compilation internally.

## 4. Nested instructions bound again on every run

**Cause.** Only root instructions were prepared (`prepare_constant`, called in
`add_transform`). An instruction inside `iter`, `on*` or a block was bound again
on every application: table lookup, parameter resolution, clone and `set_params`,
which in `raw`, `rfw` and the like recompiles the regex. Even if the child had
been prepared, `impl Clone for TokenWrapper` dropped the cache, and parameter
resolution cloned the child on every run of the parent.

**Reproduction.** In blocks, 2,000 iterations:
`iter 2000 times onln 3 apply raw a A` → 7.0 ms; the same structure with `tua` (no
regex) → 0.79 ms. About 88% of the time went into recompiling the same regex.

**Implications.** The per-line pattern (`iter` + `onln`) and any block called
several times paid for compilation on every step; on large texts with many lines
that cost dominates.

**Fix.** (a) `prepare_constant` prepares nested children first and accepts
literal instruction parameters; (b) the prepared cache is shared (`Arc`) between
internal clones; (c) `iter` and `on*` declare `supports_preparation` (immutable
state); (d) the only public exit of wrappers, `get_transform_vec`, returns copies
without the cache, keeping the documented guarantee that an edited public
template never uses a stale cache. Dynamic parameters (`{{ }}`, `[[ ]]`,
references) are still resolved on every run.

## 5. Line scanner decodes character by character

**Cause.** `lines()` (`src/utils/lines.rs`) looks for terminators with
`char_indices().find(is_break)`, decoding each character. Every recognized
terminator starts with an ASCII byte (`\n \r \v \f`) or with the lead bytes `0xC2`
(NEL) and `0xE2` (LS/PS), which are never continuation bytes; one can search bytes
and confirm only at those points.

**Reproduction.** A 90 MB document, 2 M lines: `null` 47 ms,
`onln <last> apply tua` 156 ms, `dln <last>` 386 ms. The phase 3 benchmark showed
the same: locating lines dominates the cost of the `on*` instructions.

**Implications.** It affects every line instruction, the `on*` instructions and
the debug trace (`Size::of`).

**Fix attempted and dropped.** A byte search confirming UTF-8 at the `0xC2`/`0xE2`
bytes, without `unsafe` or new dependencies. Isolated measurement (release, 3 runs):

| Document | `char_indices` (current) | byte by byte | bytes in blocks of 32 |
| --- | ---: | ---: | ---: |
| 2 M lines of 40 B (accents, emoji) | 98.5 ms | 83.8 ms | 120.3 ms |
| 900 k ASCII lines of 100 B | 84.3 ms | 76.7 ms | 121.0 ms |
| 9 k lines of 10 KB (`é`) | 59.2 ms | 71.1 ms | 84.6 ms |

The gain is 9–15% on short lines, with a 20% loss on long lines of multibyte
text; the block version is worse everywhere. Under Golden Rule 11 the change is
not justified, and it was reverted. A real gain would need a vectorized search
(`memchr` or similar), a new dependency that needs approval.

## 6. Debug trace without a limit

**Cause.** Each nested step became a line kept in memory until the end of the
root step. `iter 100000 times ate x` produced 100,000 lines for a single step
(547 ms in release), and the `buffered` mode, which should keep the log out of
memory, kept them all in a `Vec<String>` before writing to the spool. Besides,
each traced container measured the whole document (characters and lines) when
opening and closing, even when nothing of it would be shown.

**Implications.** Debugging large loops flooded the output and used memory
proportional to the number of iterations; the limit the specification asks for
`rmape` did not apply to the other containers.

**Fix.** At most 20 steps listed per container, followed by `… +K steps`, as in
`rmape`. Containers past the limit are neither rendered nor measured.

## 7. Errors holding the whole document (fixed in 0.3.0)

`check_range` (used by `dlni`, `slnc` and, for parity, by `onln`/`onlni`) and the
error of `onck` put the whole text in the error's `input` field; so did the
character and word index errors (`dls`, `dla`, `dlb`, `dlc`, `ins`, `inf`,
`sslt`…) and those of `jsone`, `jsonu` and `urld`, some also in the message. On a
100 MB document one index error doubled memory use and produced huge messages.
Maintainer decision (2026-11-14): these errors keep only an excerpt,
`utils::errors::input_excerpt` (up to 80 characters followed by `… [N bytes]`).
Short texts appear whole, as before.

## Results of the fixes

Same machine and probes as the reproduction (release, mean per run).

| # | Measurement | Before | After |
| --- | --- | ---: | ---: |
| 1 | `cblk` with `end` in the middle (`ate x; end; ate y`) | `"xy"` | `"x"` |
| 1 | `iter 3 times end` + `ate y` in the same block | `"y"` | `""` |
| 2 | `iter 2 times onln 1 apply tbs` in bytecode | accepted | rejected, as in text |
| 2 | `blk b assoc iter 2 times onln … apply tbs` in bytecode | rejected | loads and runs |
| 3 | `iter 2000 times ate '[[__COUNTER__ % 10]]'` with a 1 MB variable | 89.2 ms | 4.8 ms |
| 3 | the same without the large variable | 3.7 ms | 3.8 ms |
| 4 | block `iter 2000 times onln 3 apply raw a A` | 7.0 ms | 0.23 ms |
| 4 | block `iter 2000 times onln '[[__COUNTER__ % 10 + 1]]' apply raw a A` | 12.5 ms | 7.3 ms |
| 6 | debug of `iter 100000 times ate x` | 494.6 ms, 100,000 lines | 3.0 ms, 22 lines |

In item 4, the case with an expression still compiled the expression
(`build_operator_tree`) on every iteration at that point; the regex was no longer
recompiled. (The later engine work compiles templates once; see
[the engine benchmark](../benchmarks/engine/README.md).)

Tests added (all failed before the fix, except where noted):

- `tests/on_instructions.rs`: `end_stops_the_rest_of_blocks_and_iterations`,
  `bytecode_depth_limits_match_the_text_parser`.
- `src/parser/resolve_var/preparation_test.rs`:
  `nested_instructions_are_bound_once_per_registration` (failed before),
  `exported_nested_templates_carry_no_cached_binding` and
  `dynamic_nested_parameters_are_still_resolved_per_execution`. The last two also
  passed before: they protect the guarantees the shared cache could break (an
  exported template without the cache; nothing dynamic frozen).
- `src/api/processor/buffered/adapter_tests.rs`:
  `debug_lists_at_most_twenty_steps_per_container`.

No existing test was changed, except one `use` in
`src/tokens/instructions/eval/test.rs`, which imported `build_eval_context`
through the `eval` module and now imports it from `utils::expr`, where it is
defined.
