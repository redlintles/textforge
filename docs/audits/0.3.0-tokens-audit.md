# Internal audit: `src/tokens` (0.3.0)

Scope: the 88 instructions registered at the time (`src/tokens/transforms` and
`src/tokens/instructions`) and the helpers they call directly
(`utils::validations`, `TextBuffer::repeat`). Every finding was reproduced before
any fix.

## Method

1. **Automatic differential sweep.** A helper program (not committed) runs each
   instruction in its own process, combining the edge parameters `""`, `"a"`,
   `"é"`, a ZWJ emoji, regular expressions (`.*`, `(`, `\d+`), combining marks and
   the numbers `0, 1, 2, 3, 5, 40, u64::MAX`, against 16 inputs (empty, CRLF/CR,
   LS, combining marks, emoji, JSON, `%zz`, HTML entities…). For each case it
   compares borrowed against owned input (`Cow`), buffered mode with a 1-byte
   spool, a text round trip and a bytecode round trip. It also detects panics
   (debug build, with overflow checks), runs over 0.5 s and hangs (120 s limit
   per instruction).
2. **Comparison of the two bytecode serializers**: `to_bytecode()` (the path of
   `TokenWrapper::to_bytecode_resolved`) against the generic serializer
   (`to_bytecode_unresolved`), for every instruction and parameter combination.
3. **Reading** the `transform` and `set_params` functions of every instruction,
   checking the code against each one's documentation.

Result of the sweep: no panic and no divergence between modes, text and bytecode
in 84 of the 88 instructions. The findings below come from all three steps.

## 1. `tucs` uses a byte index

`for (i, c) in input.char_indices()` compares `i` (a byte offset) with
`self.index` (a character index). With a multibyte character before the
position, the wrong character, or none, is uppercased. The symmetric `tlcs` uses
`chars().enumerate()`.

Reproduce: `tucs 1;` on `"éa"` → `"éa"` (expected `"éA"`). `tucs 1;` on `"ab"` →
`"aB"` (correct only because the text is ASCII).

Fix: enumerate characters, as `tlcs` does.

## 2. `slt`/`ctc`: off-by-one when clamping `end`

Both document that an `end` past the text is clamped to the last character, but
they clamp only when `end > len` and then require `end < len`:

| Input `"abc"` | Before |
| --- | --- |
| `slt 0 2;` | `"abc"` |
| `slt 0 3;` | `IndexOutOfRange` |
| `slt 0 4;` | `"abc"` |

The same holds for `ctc 0 5;` on `"ab cd"`. `dlc` already clamps with `>=`.

Fix: clamp when `end >= len`.

## 3. `cts` validates against characters

`cts` capitalizes word `i`, and its documentation says an `i` past the number of
words is an error. The code validated with `check_index_against_input`
(characters), so `cts 3;` on `"ab cd"` (2 words, 5 characters) returned the text
unchanged without an error. `tucw`/`tlcw` already use
`check_index_against_words`.

`ctr` also validated its start against characters, but clamped the end to the
word count first, so the result was an error anyway, with the wrong message
("Start index must be smaller than end index" for `ctr 2 3;` on `"aa bb"`).

Fix: validate against words in both.

## 4. `cfw`/`clw` and whitespace

- `cfw` capitalized the first character of the text: with leading whitespace
  (`"  ab cd"`) nothing changed.
- `clw` looked for the last `' '`: with a tab or a line break (`"ab\ncd"`) it
  capitalized `ab`; with a trailing space (`"ab cd "`) nothing changed. The
  documentation says the last word comes from splitting the text on whitespace.

Fix: find the first and last word with `char::is_whitespace`, as
`split_whitespace` defines words, without touching the rest of the text.

## 5. `padl`/`padr`: panic with a huge length

`padl a 18446744073709551615;` made `extend_string` collect a `String` with an
impossible capacity → a `capacity overflow` panic (Golden Rule 2). A large but
representable length aborted the process for lack of memory.

Fix: compute the size in bytes with checked arithmetic and reserve with
`try_reserve`, returning a `TextForgeError`, as `rpt` already did.

## 6. `eval`/`rmp`: `to_bytecode()` without parameters

Both called `to_bytecode!(opcode, [])`. Writing files uses the generic serializer
and worked, but the public `TokenWrapper::to_bytecode_resolved` uses
`to_bytecode()` and produced a record the reader rejects.

Reproduce: `read_from_text("rmp a;")?.to_bytecode_resolved(&mut ctx)` → 13 bytes,
parameter count 0 (the generic serializer writes 30).

Fix: write the parameters, with a round-trip test.

## 7. `unwrap()` in main code

- `ctc`: two `unwrap()` calls on `nth(...)`, justified by a comment.
- The `Default` of `raw`, `rfw`, `rlw`, `rcw`, `rnw`, `rmp`, `sslt` and `emj`:
  `Regex::new("").unwrap()`, which also compiled a regex on every `default()`.

Fix: in `ctc`, propagate the error; for the regexes, one shared static empty
regex (the pattern of `utils/regexes.rs`), cloned in `Default`.

## 8. Buffered `rpt` can fill the disk

`TextBuffer::repeat` only refused when `len × times` overflowed `u64`. With 1 byte
and `times = u64::MAX` the product fits, and the loop wrote 64 KiB blocks to the
temporary file until the disk was full (the normal mode fails at once, when
reserving memory). Deliberately not reproduced, to avoid filling the disk;
reading the loop is enough.

Proposal: an output size limit (for example in `ExecutionProfile`) or a check of
free space first. Any limit is a contract decision.

## 9. Word instructions erase formatting

`tucw`, `tlcw`, `cts` and `ctr` rebuilt the text with `split_whitespace` + `' '`:
`cts 0;` on `"line one\nline two"` → `"Line one line two"`, and double spaces
became one. For a text-processing DSL, removing line breaks when capitalizing a
word seems unwanted, but it was the behavior recorded in the parity tests with
0.2.0 (`tests/data/allocations`). The `j*c` instructions (camel, snake…) join
words on purpose and are out of scope.

Proposal: change only the word, keeping the original separators.

## 10. `start == end` in inclusive ranges

`check_chunk_bound_indexes` required `start < end`, so `dlc 1 1;`, `tucc 1 1;`
and `onck 1 1 apply …;` were errors, although the documentation describes
inclusive ranges (where a one-character range is natural).

## 11. Minor inconsistencies

- `tucc`/`tlcc` validated `end` before clamping it, so the clamping code never
  ran and an `end` past the text was an error, unlike `slt`/`ctc`/`dlc`.
- `dlc` on empty text returned `""` for any indices, without an error.

## Results of the fixes

| # | Commit | Test that reproduces the previous behavior |
| --- | --- | --- |
| 1 | `fix(tucs): index characters, not bytes` | `tucs/test.rs`: `index_counts_characters_not_bytes` |
| 2 | `fix(slt, ctc): clamp an end equal to the text length` | `slt`, `ctc`: `end_equal_to_the_length_is_clamped_like_larger_ends` |
| 3 | `fix(cts, ctr): validate word indices against the word count` | `cts`: `index_counts_words_not_characters`; `ctr`: `start_counts_words_not_characters` |
| 4 | `fix(cfw, clw): find the first and last word across any whitespace` | `cfw`: `leading_whitespace_is_skipped`; `clw`: `transform_ignores_trailing_whitespace_and_splits_on_any_whitespace` |
| 5 | `fix(padl, padr): report impossible padding sizes instead of panicking` | `padl`, `padr`: `huge_lengths_are_errors_not_panics` |
| 6 | `fix(eval, rmp): serialize their parameters in to_bytecode` | `tests/bytecode_paths.rs` (both serializers, for every instruction) |
| 7 | `refactor(tokens): remove unwrap from instruction code` | the existing tests of `ctc` and of the regex instructions |

The deliberate behavior changes (3 and 4) change results recorded in
`tests/data/allocations/baseline.json`: the entries of `ctr`, `cts`, `cfw` and
`clw` were re-recorded with the corrected results, and the characterization test
of the `clw` quirk (`"foo "` unchanged) was replaced. A processor doctest that
relied on the silent `cts` now uses an existing word.

After the fixes, the full differential sweep (81 instructions; `rpt`, `iter`,
`end` and the file instructions are excluded by nature) finds no panic and no
divergence, including `padl`/`padr` with `u64::MAX`.

## Maintainer decisions (items 8 to 11)

The maintainer decided that a transform must not do more than is expected of it,
and that work-multiplying operations need generous default limits that users can
raise or turn off.

| # | Commit | Result |
| --- | --- | --- |
| 8 | `feat(profile): limit instructions that multiply work` | `max_generated_bytes` (2 GiB) for `rpt`/`padl`/`padr` and `max_iterations` (10,000,000) for `iter`, in `ExecutionProfile`, `.txfrc` and the `txf` flags; `tests/limits.rs` |
| 9 | `fix(words): change only the chosen words and keep the separators` | `rewrite_words` in `utils/allocation.rs`; only the chosen words change, with no copy when nothing changes |
| 10 | `fix(ranges): accept start == end in inclusive ranges` | `tests/ranges.rs` |
| 11 | `fix(ranges): clamp the end consistently and reject empty text in dlc` | `tests/ranges.rs`; a start past the text is always `IndexOutOfRange` |

Afterwards the differential sweep also covers `rpt` and `iter` with `u64::MAX`
(83 instructions) and finds no problem: both fail at once with the limit error.
The affected entries of `tests/data/allocations/baseline.json` were re-recorded
in each commit.
