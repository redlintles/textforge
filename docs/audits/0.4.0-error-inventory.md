# Error inventory (before 0.4.0)

Where `TextForgeError`s are created, what they carry and what was missing for
the error reports and `tryi` of 0.4.0. Counted on `main` after the `fix/cli`
merge (5204cff) with `grep` over `src/` (bindings and test modules excluded).
The redesign this inventory led to is described in
[error handling](../error-handling.md).

## What an error carried

`TextForgeError` had three fields: the code with its message, `instruction`
and `input`.

- `instruction` is filled in one place for errors raised while running:
  `TokenWrapper::locate` writes the source line of the innermost instruction
  when the error left it empty. Parse errors get `file:line ›` from
  `read_from_file`, joined pipelines `ppjn file:line ›` from `joins::in_join`,
  and `txf` adds `input line N ›` or `input chunk N ›`.
- `input` is an excerpt of the text (rule 20), a parameter or a path,
  depending on the error.
- There was **no** list of the containers the error passed through (`iter`,
  `cblk`, `on*`, `ppjn`), **no** resolved parameters, and the cause of an I/O
  or regex error was only part of the message.
- `Display` printed three colored lines (`error[N]: message`, `in:`,
  `input:`), so the ANSI codes reached logs written by library users.

## Findings

1. **The safety limits shared code 20 with structural rules.** `max_iterations`
   and `max_generated_bytes` were `ValidationError`s, like a reserved variable
   name or a nesting limit, so a caller could not tell them apart without
   reading the message. `tryi` must never ignore a limit (rule 19), so the
   limits need a code of their own.
2. **`TextParsingError` is also a run-time error**: a pattern that is only
   known at run time (`raw '{{p}}' x;`) fails with code 17, the code of a
   pipeline that does not parse. Whether an error is ignorable therefore
   depends on *when* it happens, not only on its code: `tryi` only sees errors
   raised while its instruction runs, which settles it.
3. **Codes 7 and 11 are never created.** They stay reserved: the numbers are
   stable.
4. **Errors had no context of the run.** The instruction field named the
   innermost instruction, not the `iter`, block or joined pipeline around it,
   nor the values its parameters had (`dlc [[n]] 9;` showed the template, not
   `n`'s value).
5. **`ErrorManager` was write-only.** The processor recorded every error it
   returned into a private `ErrorManager` (13 call sites, each cloning the
   error) that nothing ever read, and that grew for the lifetime of the
   processor.
6. **Messages are already descriptive** (0.3.1 rewrite) and are kept; what
   changes is what surrounds them.

## What 0.4.0 does about them

- Code **31 `LimitExceededError`** for the safety limits; it is the only code
  that is not ignorable (`TextForgeErrorCode::ignorable`).
- Errors carry `details`: the trace of instructions they passed through, with
  their source line and a note (`__COUNTER__ = 1`, the block's step), the
  resolved parameters of the failing instruction with their names, and the
  cause. They are added only on the error path.
- `Display` is one plain line; `TextForgeError::report` renders the full,
  colored report.
- The processor no longer records errors in an `ErrorManager`; the type is
  deprecated. Errors ignored by `tryi` are kept per run and shown by the debug
  methods.
